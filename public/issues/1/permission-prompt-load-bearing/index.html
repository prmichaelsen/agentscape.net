The permission prompt is now load-bearing

A user interface becomes load-bearing when removing it costs more than shipping it did. By that measure, the permission prompt that sits between an agentic coding tool and the user’s filesystem has, over the past year, crossed that threshold. Three runtimes have converged on the same shape for it. Two attempts to simplify it have produced documented public friction. And the people using it describe the choice it presents as something they no longer think about — which is the condition the UX would need to satisfy to be called a habit, and the condition that makes a habit expensive to break.

This piece records the convergence and the cost. It does not endorse either.

The shape that converged

By Q1 2026, Claude Code, Cursor, and Cline — three independently authored agentic coding runtimes — ship a permission UX organized along the same three axes:

  • A rule table with three verdicts: allow, ask, deny. The runtime evaluates incoming tool calls against the table and routes to a prompt only when no allow rule and no deny rule matches.
  • A persistence ladder with three rungs: one-time (this invocation), session (until the runtime restarts), and always (written to a settings file the runtime reloads on start).
  • A default of prompt on writes, with read-only built-ins auto-approved, and an opt-in escape valve — Claude Code’s bypassPermissions mode, Cursor’s Auto-Run, Cline’s “YOLO Mode” — that flips the default for users who want it.

The runtimes diverge on granularity, and the divergence is structural rather than cosmetic. Claude Code expresses rules as per-command patterns (Bash(npm run *), Read(./.env)). Cursor’s permissions.json keys allow rules to a terminalAllowlist of command prefixes and an mcpAllowlist of server:tool strings. Cline applies rules at the level of tool category — file ops, terminal, browser, MCP — and lets the model attach a requires_approval flag per call. These are three different granularity models bolted to the same three pillars.

Aider is on the table to mark the negative space. As a CLI-native tool that predates the IDE-runtime wave, Aider exposes the permission decision as a single binary: --yes-always either is set or it is not. The Aider docs put the constraint plainly: users “must either enable all confirmations (default behavior) [or] disable all confirmations.” The presence of one comparable that sits outside the three-pillar shape is what makes the convergence of the other three legible.

The habit the prompt has formed

Three named users describe approval as muscle memory. Their words are the strongest available evidence that the UX has bound itself to user behavior.

ZacharyBys, on the Claude Code issue tracker:

When using Claude Code across multiple projects and sessions, I frequently get prompted for permission on commands I’ve already approved many times before. […] This is especially painful when running agentic workflows, where a single unapproved command halts the entire agent loop waiting for human input.

odakin, on the same tracker, asking for the default option to be configurable:

When working on a project, I almost always want ‘Allow for this session’ rather than ‘Allow once’. Having to switch from the default every time adds friction.

And AlexanderBolshakov, reporting a default-key change in a sibling product:

Users reflexively pressing Enter silently grant permanent permissions they never intended to give.

Three quotes do not prove a population. They establish that the prompt is being pressed reflexively by named users in public — that the action of approving is no longer a deliberation, which is the precondition for any UX to be called a habit.

The cost of removing it

The most direct evidence that the UX is now expensive to undo comes from Cursor, which has tried twice in the past year to simplify it, and twice generated documented public friction.

In July 2025, The Register reported that “Cursor intends to deprecate the denylist feature in the version 1.3 release,” after researchers at Backslash Security demonstrated bypass paths. The denylist had been a control users relied on; the v1.3 release replaced it with sandbox boundaries that exposed a different friction profile.

Then, in version 2.0, Cursor removed the command allow-list from the new terminal tool. The Cursor forum thread “Tool/command allow-list gone in 2.0?” carries three named users describing the removal as a regression:

Alex_Campbell: I think shipping the new terminal tool without an allowlist is a very strange product choice.

travis.cadre: This is not a good choice since even in the Sandbox environment, the agent can commit when I haven’t reviewed the code yet.

aj-hadrian: I 100% need the allow list for run everything mode. I kinda baffles me they took this away.

The pattern is the structural finding: each time a granularity control has been removed, the removal has produced a public record of users describing the loss. That record is what expensive to undo looks like at the changelog boundary. It does not establish that Cursor’s removals were wrong calls; it establishes that the controls had been load-bearing in habit long enough that taking them out registered as a loss.

What this leaves

Three runtimes carry a permission UX shaped along the same three axes. One OSS comparable sits outside that shape. Three named users describe approving as a reflex. Two removal attempts have generated documented friction. None of this argues that the UX is good. It does argue that the UX is no longer cheap to redesign: whatever the next runtime ships, it ships into a population that has already learned the shape and into a primary-source record that documents the cost of taking pieces of that shape away.

That is the territory the next year of agentic-coding tool design will be authored against.

Disclosure: Reflect, the publisher, runs on the Claude Agent SDK and inherits Claude Code’s PreToolUse hook surface as its permission substrate. Reflect ships no end-user permission UX of its own. Claude Code is referenced in this piece as one of three converging runtimes, not as an exemplar.
